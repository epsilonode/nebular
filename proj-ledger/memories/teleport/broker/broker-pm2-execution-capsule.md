# PM2 Role And Execution Capsule

@superseded Do not implement this resident-per-process capsule topology. It was rejected because it adds one persistent Bun runtime, event loop, handles, and memory footprint for every managed process. The active direct-materialization contract is `memories/teleport/broker/broker-direct-receiver-materialization.md`; retain this card only as rejected-design rationale.
@artifact The execution capsule is a privileged runtime mode inside the existing bundled `broker.js` artifact. It is not a fifth runtime file, package, native executable, container, VM, or separately installed daemon. Representative modes are `broker.js execute-recipe`, broker administration, credential CAR import/export, and diagnostics.
@role PM2 is the mandatory Windows V1 receiver for every executable recipe. It restores OS-like affordances for agents: durable process identity, cross-invocation status, output logs, restart facts, exact cancellation targets, and lifecycle operations independent of a blocked initiating shell.
@capsule PM2 manages `broker.js execute-recipe` as an execution capsule representing one recipe lane/attempt. The capsule launches and owns the requested command subtree, so the backend still supervises the complete workload while the capsule adds recipe semantics, credential isolation, progress evaluation, and Windows tree containment.
@why_wrapper Directly placing a secret-bearing target in PM2 requires sending its secret environment through PM2 materialization and metadata. The capsule lets PM2 manage the process without receiving raw credentials and provides a stable receiver protocol for native, interpreted, Mise, uv, and other commands.
@topology The process topology is `agent -> recipe-runner.js -> short-lived broker.js control over inherited Bun IPC -> PM2 -> broker.js execute-recipe capsule -> requested command -> descendants`. PM2 owns the capsule lifecycle; the capsule owns and reports the complete requested-command subtree.
@identity Derive a sanitized stable PM2 name from repository identity, recipe id, and execution lane; maintain a distinct unique attempt id. Materialize nonsecret provenance metadata sufficient to detect exact reuse/mismatch without exposing credential values or encrypted-CAR material.
@identities Keep three identities distinct: durable `RecipeId`, stable exact-target `ProcessName` for the repository/recipe/lane, and unique `ProcessAttemptId` for one start or restart epoch. PM2 operations address the stable name; output, heartbeat, lease, and terminal records carry the attempt id so epochs cannot mix.
@config Use fork mode, one instance, watch disabled, explicit canonical cwd, pinned Bun plus bundled `broker.js`, argv atoms, filtered/scrubbed environment, hidden Windows console where appropriate, bounded `kill_timeout`, merge-log policy, readiness handshake, bounded restart delay/count, and configured non-restarting exit codes.
@no_secrets PM2 config, `pm2_env`, names, args, ecosystem files, dumps, logs generated by the capsule itself, and status metadata contain no credential, PIN/passphrase, decrypted transfer, keychain return value, or secret-derived identifier.
@start The control broker performs preflight and exact-name conflict/reuse checks before PM2 start. The capsule repeats repository/recipe/grant validation, acquires credentials, establishes Job Object containment, starts the target, and signals PM2 ready only after the recipe readiness policy succeeds.
@start_sequence Startup is ordered and fail-closed: runner sends a versioned request over inherited IPC; control broker resolves Git/worktree and recipe revision; evaluates policy/grant/credential slots; performs nonsecret receiver preflight; materializes an exact nonsecret PM2 capsule config; PM2 starts the capsule; capsule repeats authority validation; acquires credentials from `Bun.secrets`; constructs the target environment; creates Job Object containment; launches the target; starts output/heartbeat/probe/deadline evaluation; then emits ready only after declared readiness succeeds.
@start_failure Failure before target launch leaves no target. Failure after partial launch cancels and verifies the exact subtree before reporting terminal failure. A control broker cannot report successful start merely because PM2 accepted the capsule config.
@restart A restart creates a fresh capsule instance and fresh attempt epoch. It must revalidate recipe revision, grant generation, expiry, credential slots, and restart policy before secret acquisition. Expired/revoked/drifted authority exits with a configured stop code so PM2 does not enter a restart storm.
@status Treat PM2 as runtime truth for capsule presence, PID, daemon state, restart count, and PM2 lifecycle. Combine it with capsule heartbeat/probe/tree facts for universal health; PM2 `online` never proves the target is ready or progressing.
@snapshot The capsule publishes a typed snapshot containing attempt/repository/recipe/receiver identity; universal and backend states; sequence; capsule and target PIDs/tree facts; start, ready, heartbeat, progress, and output times; uptime/restarts; deadlines; ports/probes; stdout/stderr offsets and truncation; redacted lease expiry; blockers; cleanup state; and next actions.
@snapshot_shape A representative shape is `AttemptSnapshot { attemptId, recipeId, repositoryId, receiverId, sequence, state, backendState, capsulePid, targetPid?, startedAt, readyAt?, lastHeartbeatAt, lastProgressAt?, stdoutOffset, stderrOffset, restartCount, deadlines, readiness, liveness, blockers, cleanup?, nextActions }`; exact wire fields remain versioned and boundary-decoded.
@output The capsule relays target stdout/stderr to its own streams for PM2 retention while separately maintaining bounded cursor facts and heartbeat summaries. Log location and offsets are agent-visible; secret-bearing output follows the vetted-recipe/well-behaved-agent threat model.
@tick_tock Publish a monotonic `tick` sequence for state/fact snapshots and independent stdout/stderr `tock` byte offsets for bounded output deltas. Every cursor and chunk includes attempt identity; stale cursors produce an explicit gap/full-snapshot response rather than mixing output across restarts.
@progress Evaluate progress from recipe-selected output advancement, heartbeat advancement, readiness/liveness probes, child/process facts, domain milestones, and monotonic time. Examples: PM2 online plus current heartbeat and healthy probe is running/ready; no output with an allowed quiet policy is quiet-allowed; stale heartbeat plus failing probe is stalled; active output with an overdue required milestone is degraded or stalled.
@self_stall A capsule cannot reliably diagnose its own completely stalled event loop. Agent/control-side polling detects stale capsule heartbeat while PM2 still reports online and may issue exact cancellation. PM2 crash/restart handles capsule exit; stale-heartbeat policy handles a live but nonresponsive capsule.
@stop PM2 stop/delete addresses the exact stable name. The capsule handles shutdown message/signal, cancels probes/timers, gracefully stops the target, waits the recipe grace, closes the Job Object or force-kills descendants, verifies cleanup, releases leases, writes terminal facts, and exits.
@cancel_sequence Cancellation is ordered and observable: resolve exact stable name and attempt; record request/reason/initiator; transition to cancellation-requested; ask the capsule/target to stop gracefully; publish progress during the grace interval; escalate through Job Object/tree cleanup; verify descendant absence; release the secret lease and transient resources; write redacted terminal/cleanup facts; exit the capsule; then stop/delete or retain the PM2 record according to retention policy.
@cancel_outcome Distinguish cancellation accepted, graceful completion, forced completion, partial cleanup, stale-attempt mismatch, already terminal, and recovery-required. Never equate sending a stop signal with verified cancellation.
@windows Use a Job Object as the authoritative capsule subtree boundary on Windows, with kill-on-close and verified descendant cleanup. PM2 `kill_timeout` is the outer safeguard for an unresponsive capsule, not the only tree-containment mechanism.
@control Reuse the bounded `pk` PM2 adapter operations: daemon probe, connect, list/get exact name, start typed config, stop exact name, delete exact name, and disconnect. Preserve deadlines and a guarded forced client-process termination fallback for Bun/Windows PM2-handle regressions.
@retention One-shot PM2 records/logs may be retained for a bounded diagnostic interval and then exact-deleted; long-lived/service records remain while active or intentionally stopped according to recipe policy. Durable summarized terminal facts live outside PM2 and contain no secrets.
@not_container The capsule provides lifecycle ownership and observation, not kernel isolation. It does not sandbox the target, protect against malicious same-user code, prevent an authorized process from reading its environment or printing a credential, guarantee JavaScript memory erasure, or make a broad provider credential least-privilege.
@not_manager The capsule is not a second general process manager and does not replace PM2. It interprets one admitted recipe attempt, owns one command subtree, and projects facts into the universal receiver contract. It does not offer arbitrary process discovery, broad kills, global service administration, or ad hoc shell execution.
@not_authority PM2 online state, process ownership, a recipe digest, or possession of an opaque grant reference never grants credential authority. The capsule repeats broker policy and grant validation before each acquisition/restart.
@proof Test command success/failure, readiness, quiet/stall, output saturation, cancellation, capsule crash, target escape attempt, Job Object cleanup, PM2 daemon loss, restart policy, stop exit codes, exact reuse/mismatch, stale process records, idempotent delete, and secret absence from all PM2-visible surfaces.
@proof_sequence Add ordered-event assertions for every startup and cancellation phase, including partial-start rollback, readiness-before-success prohibition, stale-heartbeat detection from outside the capsule, restart epoch isolation, cursor gaps, lease release, forced cleanup verification, and recovery-required outcomes.
